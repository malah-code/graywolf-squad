## Clarifications

### Session 2026-11-01

- Q: How should database schema migrations be orchestrated in the production stack? → A: Dedicated `db-migrate` one-shot container in `docker-compose.prod.yml` that waits for PostgreSQL health, executes `scripts/db-migrate-init.sh` (`pnpm migrate:up`), and exits `0` before `orchestrator` starts via `condition: service_completed_successfully`.
- Q: How should the web dashboard SPA and reverse proxy be packaged and served in production? → A: Hardened Nginx Alpine container (`docker/dashboard/Dockerfile.prod` + `docker/dashboard/nginx.conf`) on `edge-net` providing SPA fallback routing (`try_files $uri $uri/ /index.html`), gzip/cache control, and strict security headers (`CSP`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`).
- Q: Where and how should the zero-prompt Master Key (`master.key`) be managed and mounted in the production container? → A: Persistent named volume `graywolf_keys` mounted to `/home/graywolf/.graywolf` (`0600` permissions), auto-generated by `scripts/install.sh` if absent, never exposed in container environment variables.
- Q: What hardware profiling criteria and limits should the bootstrap installer apply for edge/constrained hosts? → A: Auto-detect host RAM: if $\le$ 8GB (e.g. Raspberry Pi 5 / ARM64), set `DEPLOYMENT_TOPOLOGY=solo`, `MAX_CONCURRENT_CONTAINERS=1`, Valkey `maxmemory 256mb` (`noeviction`), and serialized testing; otherwise set `MAX_CONCURRENT_CONTAINERS=3` and Valkey `maxmemory 512mb`.
- Q: What is the verification scope for the automated production smoke test suite? → A: Three-layer automated test harness: unit validation of Dockerfiles/Nginx configurations, integration validation of Compose YAML 4-network topology and volume mappings, and an E2E smoke test verifying installer prerequisite detection, `--dry-run` credential generation, migration idempotency, and `/health` probe HTTP 200 response.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Hardened Multi-Stage Production Images & SPA Serving (Priority: P1)

A self-hosting Lead Developer or DevOps Operator wants to deploy the Graywolf Squad Control Plane and Web Cockpit using minimal, production-hardened container images on either standard cloud servers (`x86_64`) or edge hardware (`ARM64` / Raspberry Pi 5), ensuring the runtime excludes development tools, runs under an unprivileged user account, and serves the web interface with strict security headers and client-side routing support.

**Why this priority**: Production container images are the foundational artifact for every self-hosted deployment; running development containers or root processes in production introduces unacceptable security and memory overhead, especially on 8GB RAM constrained hosts.

**Independent Test**: Can be independently tested by validating the production build definitions and container configuration artifacts for multi-stage compilation, non-root execution (`uid: 1001`), build-context exclusion rules, Content Security Policy headers, and single-page application route fallback.

**Acceptance Scenarios**:

1. **Given** the repository source code, **When** the production orchestrator image definition is inspected and built, **Then** it uses a multi-stage build that compiles the application, strips development dependencies, copies migration and runtime assets, runs as non-root user `graywolf` (`uid: 1001`), and exposes only port `3000` (Control Plane) and port `3001` (Agent Relay Protocol).
2. **Given** the web dashboard source code, **When** the production dashboard image definition is inspected and built, **Then** it compiles the static frontend bundle in an isolated build stage and serves assets in the runtime stage with SPA fallback routing (`index.html` for deep links) and hardened HTTP security headers (`Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`).
3. **Given** a build context on either `linux/amd64` or `linux/arm64`, **When** the `.dockerignore` rules are evaluated, **Then** local development artifacts (`node_modules`, `.git`, `.agents/dataset`, `storage`, test outputs, and local `.env` files) are excluded from the build context to prevent secret leakage and minimize image build time.

### User Story 2 - Turnkey Production Stack Topology & Automated Schema Migration (Priority: P1)

A Platform Operator wants a dedicated production orchestration definition (`docker-compose.prod.yml`) that preserves the 4-network physical isolation architecture, automatically runs all pending database schema migrations to completion before the control plane starts accepting traffic, and provides a complete template of production environment settings.

**Why this priority**: Without automated pre-boot schema migrations and strict network isolation in the production stack definition, first-time deployments fail with missing database tables or accidentally expose internal control buses and the host container daemon.

**Independent Test**: Can be independently tested by parsing and validating `docker-compose.prod.yml`, `scripts/db-migrate-init.sh`, and `.env.production.example` to confirm 4-network segmentation, service health dependency ordering (`postgres-shared` healthy ➔ `db-migrate` completed successfully ➔ `orchestrator` starts), persistent volume mappings, and complete environment variable parity.

**Acceptance Scenarios**:

1. **Given** a fresh production deployment, **When** the stack launches via `docker-compose.prod.yml`, **Then** the `db-migrate` initialization service waits for the database healthcheck to pass, idempotently applies all schema migrations in lexical order, and exits with code `0` before the `orchestrator` service boots.
2. **Given** the `docker-compose.prod.yml` topology definition, **When** network attachments and daemon access are audited, **Then** all 4 segmented networks (`edge-net`, `control-net` internal, `daemon-net` internal, `runner-net` egress-capable) are preserved, raw `/var/run/docker.sock` is mounted read-only exclusively into `docker-proxy` (`EXEC=0`, `VOLUMES=0`), and persistent named volumes protect database state, cache stores, task worktrees, and envelope encryption keys across restarts.
3. **Given** an operator configuring a new host (Standard 16GB+ or Constrained 8GB ARM64), **When** `.env.production.example` is reviewed, **Then** every required production setting (database credentials, ports, deployment topology, hardware admission profile overrides, and key vault paths) is documented with safe defaults and zero plaintext production secrets.

### User Story 3 - Zero-Friction Bootstrap Installer & Cold-Boot Smoke Verification (Priority: P2)

A Solo Developer or Small Team Lead wants a single-command POSIX bootstrap script (`scripts/install.sh`) that verifies host prerequisites, generates cryptographically random service credentials and the `0600` master Key Encryption Key if not already present, and verifies that the entire release package passes an automated cold-boot smoke test.

**Why this priority**: Manual multi-step setup is error-prone; a deterministic installer with `--dry-run` capability and an automated end-to-end smoke harness guarantees that the `v0.1.0-p0` release works out of the box on clean Linux and edge hosts.

**Independent Test**: Can be independently tested by executing `scripts/install.sh --dry-run` against a temporary target directory and running the automated smoke test suite (`tests/e2e/production-compose-smoke.test.ts`) to verify credential generation, `0600` file permissions, idempotent re-runs, migration execution, and health probe responses.

**Acceptance Scenarios**:

1. **Given** a clean host environment without an existing `.env.production` or master key, **When** the operator runs `scripts/install.sh` (or `scripts/install.sh --dry-run`), **Then** the script checks for required container runtime prerequisites, generates `.env.production` with cryptographically random database/session secrets, initializes `.graywolf/master.key` with strict `0600` permissions, and never overwrites existing credentials on subsequent runs.
2. **Given** an ARM64 constrained host ($\le$ 8GB RAM, such as Raspberry Pi 5), **When** `scripts/install.sh` detects the host architecture and memory, **Then** it automatically configures the constrained hardware profile (`DEPLOYMENT_TOPOLOGY=solo`, `MAX_CONCURRENT_CONTAINERS=1`, 2GB container memory ceiling) in the generated configuration.
3. **Given** the complete `v0.1.0-p0` production artifacts, **When** the automated production smoke test suite runs, **Then** it verifies all production Dockerfiles, compose service dependencies, migration script idempotency, bootstrap installer safety, and control plane `/health` readiness probes with 100% pass rate.

### Edge Cases

- **Existing `.env.production` or `master.key` on Re-Install**: Running `scripts/install.sh` on an already-initialized host MUST preserve the existing `.env.production` and `~/.graywolf/master.key` without overwriting or rotating keys, preventing accidental loss of encrypted `secret_vault` entries.
- **Database Migration Failure on Boot**: If `scripts/db-migrate-init.sh` encounters a database connection timeout or a malformed migration script, it MUST exit with a non-zero status code and prevent the `orchestrator` service from starting in an inconsistent schema state.
- **Constrained Host Memory Detection ($\le$ 8GB RAM)**: When deployed on an 8GB RAM edge host (e.g., Raspberry Pi 5), the bootstrap script and compose configuration MUST cap container concurrency at `1` and Valkey memory at `256mb`–`512mb` (`noeviction`) to prevent host kernel OOM panics.
- **Deep-Link Browser Refresh on Dashboard SPA**: Navigating directly to a nested route (e.g., `/projects/proj-1/tasks/TASK-101`) in the production dashboard container MUST serve `index.html` with HTTP `200` rather than returning an Nginx `404 Not Found`.
- **Missing Container Runtime Prerequisites**: If `docker` or `docker compose` is absent or the daemon is unreachable when running `scripts/install.sh` (outside `--dry-run` mode), the script MUST fail fast with a clear, actionable diagnostic message and non-zero exit code before mutating partial state.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide multi-stage production container build definitions for both the Control Plane Orchestrator (`docker/orchestrator/Dockerfile.prod`) and the Web Dashboard (`docker/dashboard/Dockerfile.prod`) accompanied by a repository `.dockerignore` file that excludes development dependencies, local secrets, git history, and test artifacts.
- **FR-002**: The production Orchestrator image MUST execute as a non-root user (`graywolf`, `uid: 1001`), include compiled production code (`dist/`), runtime relay scripts (`src/relay/`), and database migrations (`migrations/`), and expose exclusively ports `3000` (Control Plane) and `3001` (ARP WebSocket).
- **FR-003**: The production Dashboard image MUST compile static frontend assets and serve them with SPA route fallback (`try_files $uri $uri/ /index.html`) and hardened HTTP response headers (`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Content-Security-Policy`).
- **FR-004**: System MUST provide a production compose specification (`docker-compose.prod.yml`) that preserves the 4-network physical isolation model (`edge-net`, internal `control-net`, internal `daemon-net`, and `runner-net`), restricts Docker socket access to `tecnativa/docker-socket-proxy` (`EXEC=0`, `VOLUMES=0`), and configures restart policies (`unless-stopped`), resource limits, and healthchecks for all services.
- **FR-005**: System MUST provide an idempotent database migration initialization script (`scripts/db-migrate-init.sh`) and a dedicated `db-migrate` service in `docker-compose.prod.yml` that waits for PostgreSQL readiness, executes `pnpm migrate:up` (and any SQL initialization scripts), and gates `orchestrator` startup on `service_completed_successfully`.
- **FR-006**: System MUST provide a comprehensive `.env.production.example` template documenting all required production environment variables (`POSTGRES_*`, `PORT_CONTROL`, `PORT_ARP`, `DEPLOYMENT_TOPOLOGY`, `GRAYWOLF_KEK_PATH`, `MAX_CONCURRENT_CONTAINERS`, `LITELLM_MASTER_KEY`, and OTLP opt-in flags) with zero hardcoded live secrets.
- **FR-007**: System MUST provide a POSIX-compliant bootstrap installer script (`scripts/install.sh`) supporting `--dry-run` and custom target directory flags that checks runtime prerequisites, auto-detects host CPU/RAM profile (Standard vs. Constrained $\le$ 8GB RAM), generates `.env.production` with cryptographically random secrets if absent, and provisions `.graywolf/master.key` with strict `0600` permissions without overwriting existing files.
- **FR-008**: System MUST provide an automated verification suite (`tests/unit/production-dockerfiles.test.ts`, `tests/integration/compose-prod-topology.test.ts`, and `tests/e2e/production-compose-smoke.test.ts`) that validates the production Dockerfiles, compose topology, migration runner, and bootstrap installer across standard and constrained host profiles.

### Key Entities

- **Production Compose Stack (`docker-compose.prod.yml`)**: Declarative multi-service deployment specification binding `docker-proxy`, `postgres-shared`, `valkey`, `db-migrate`, `litellm-proxy`, `orchestrator`, and `dashboard` across the 4 segmented networks and persistent volumes.
- **Database Migration Runner (`scripts/db-migrate-init.sh`)**: Pre-boot initialization script that verifies PostgreSQL connectivity and applies canonical schema migrations idempotently before control plane startup.
- **Bootstrap Installer (`scripts/install.sh`)**: Self-contained POSIX shell utility that profiles host hardware, initializes `.env.production` and the `0600` envelope master key, and launches or dry-runs the production stack.
- **Dashboard Nginx Configuration (`docker/dashboard/nginx.conf`)**: Hardened static web server configuration providing SPA history-mode routing, asset caching, and security headers.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of production container images run with non-root privileges for the application runtime (`uid: 1001` for Orchestrator) and exclude 100% of development-only packages (`devDependencies`) and local `.env` / `.git` directories via `.dockerignore`.
- **SC-002**: 100% of production network boundaries in `docker-compose.prod.yml` enforce the 4-network segmentation contract (`control-net` and `daemon-net` marked `internal: true`, `docker.sock` mounted read-only exclusively on `docker-proxy` with `EXEC=0` and `VOLUMES=0`).
- **SC-003**: Running `scripts/install.sh` on a clean environment completes prerequisite checks, hardware profiling, secret generation, and `0600` master key creation in under 5 seconds, and re-running the installer preserves 100% of existing credentials and keys byte-for-byte.
- **SC-004**: 100% of automated unit, integration, and end-to-end production smoke tests pass with zero regressions across the existing 487-test platform suite.

## Assumptions

- Target hosts run a Linux distribution (x86_64 or ARM64, such as Ubuntu 24.04 LTS, Debian 12, or Raspberry Pi OS 64-bit) with Docker Engine 24+ and Docker Compose v2 installed.
- TLS termination in multi-user production deployments (Topologies B and C) is handled either by an upstream reverse proxy (e.g., Caddy, Nginx, Cloudflare Tunnel) in front of `edge-net` or on `localhost` for Topology A solo developer workstations.
- Database schema migrations are managed through the repository's existing `node-pg-migrate` pipeline (`migrations/`) and PostgreSQL extension initialization (`docker/postgres/init/00-extensions.sql`).
